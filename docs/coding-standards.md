# 代码规范与功能归属

## 1. 基本规则

- 使用 Godot 4.7.x 与类型化 GDScript。
- 组合优先于继承；继承只表达稳定的“是一个”关系，不表达内容型号差异。
- 模拟层不得依赖渲染、输入、UI 或场景树查找。
- 每条业务规则只有一个权威实现，预览和正式操作必须复用它。
- 优先使用稳定 ID、`Vector2i`、小型 DTO 和纯函数作为层间边界。
- 不因方便而新增全局单例、全局信号或任意字典。

## 2. 命名约定

- 文件与目录：`snake_case`。
- 类：`PascalCase`，公共脚本使用 `class_name`。
- 方法、变量、信号：`snake_case`。
- 常量：`UPPER_SNAKE_CASE`。
- 私有成员：前缀 `_`。
- 定义 ID：小写命名空间形式，例如 `base:iron_plate`、`base:assembler_1`。
- 布尔值使用 `is_`、`has_`、`can_` 或 `should_` 前缀。
- 命令使用动词，例如 `PlaceMachineCommand`；事件使用已发生语态，例如 `MachinePlacedEvent`。

## 3. 类型与数据

- 公共方法参数、返回值、导出变量和重要成员必须显式标注类型。
- 不使用无约束 `Dictionary` 充当长期领域模型；为跨层数据建立类型化 DTO 或小型值对象。
- 可以在内部索引中使用类型化字典，例如 `Dictionary[Vector2i, int]`。
- 金额、数量、tick 和格子坐标优先使用整数。需要小数确定性时采用固定点值或明确量化规则。
- `Resource` 是静态内容模板；某局游戏状态不得写回共享 Resource。
- 缓存必须可由权威状态重建，并明确失效条件。

## 4. 类与方法职责

- 一个类只有一个主要变化原因。
- 一个方法完成一个可命名动作；复杂验证拆成可独立测试的规则。
- 查询方法不产生状态变化。
- 状态修改通过命令、服务或组件 API 完成，不允许外部直接改内部容器。
- 构造对象后应立即满足基本不变量，禁止长期存在“半初始化”对象。
- 用返回结果表达预期失败，用断言表达程序员错误，用错误日志表达无法恢复的内容或系统问题。

## 5. 继承与组合准则

适合继承：

- Godot 要求的 `Node`、`Resource`、`RefCounted` 基类。
- 少量、稳定、无内容差异的抽象基类，例如统一系统生命周期。
- 真正需要替换实现且契约固定的策略类。

适合组合：

- 机械的库存、配方加工、端口、能耗、发电、采掘、传输等能力。
- 放置规则、占地形状、科技解锁效果。
- UI 的提示、选择、过滤和展示模块。

如果添加一种机械需要创建新的机械子类，先判断它是否只是现有能力的参数组合。若是，应添加定义数据而非代码类。

## 6. 系统间通信

- 需要返回值、事务或顺序保证：直接调用明确的服务接口。
- 一对多的“事情已经发生”：发布领域事件或 Godot 信号。
- 高频模拟数据交换：系统查询组件存储，不逐实体广播信号。
- UI 不直接操作模拟组件；它提交命令并读取查询模型。
- 表现对象按实体 ID 关联，不把 Node 引用写入模拟状态。

## 7. Godot 生命周期

- `_process()`：输入采样、相机和纯表现更新。
- `_physics_process()`：需要物理同步的表现或角色运动，不承担工厂生产推进。
- `SimulationRunner`：以固定步长推进所有工厂模拟。
- `_draw()`：只绘制，不修改模拟状态。
- `_ready()`：装配引用和表现初始化，不执行依赖不确定顺序的业务逻辑。
- `_unhandled_input()`：将输入翻译成意图，不直接复制业务规则。

## 8. 模拟与表现边界

- 模拟状态是唯一权威；表现状态必须能够从模拟状态重建。
- 模拟代码不得创建、查询或保存 Sprite、TileMap、动画、音效和 UI 节点。
- View 通过实体 ID 读取只读状态或消费领域事件，不持有修改模拟组件的入口。
- View 请求改变世界时必须提交应用命令，不能直接修改库存、占用或生产进度。
- 模拟使用固定 tick；表现使用每帧更新和插值，插值结果不得写回模拟。
- 动画完成、粒子结束和音效播放均不能决定生产、拆除或科技等游戏结果。
- 地表规则读取 `TerrainState`，不能从 TileMap 图块或贴图名称反推。
- 传送带逻辑物品不等于 Sprite；渲染应可从逐物品节点替换为对象池或批量绘制。
- 相机裁剪、隐藏或销毁远处 View 不得暂停对应实体的模拟。
- 存档不得序列化表现节点和可重新生成的视觉缓存。

判断功能归属时使用以下标准：如果删除所有 Sprite、动画、音效和 UI 后，该规则仍会改变游戏结果，它就属于模拟层或应用层；如果它只改变玩家如何看到或听到结果，它就属于表现层。

## 9. 错误与结果对象

放置、拆除、研究等可预期失败使用结构化结果：

```text
PlacementResult
├─ allowed: bool
├─ reasons: Array[PlacementFailure]
├─ occupied_cells: Array[Vector2i]
└─ optional_conflicts: Array[EntityId]
```

失败原因使用枚举或类型化对象，UI 再映射为本地化文本。领域层不返回面向玩家的硬编码文案。

## 10. 功能归属表

| 功能 | 权威归属 | 不应放在 |
| --- | --- | --- |
| 世界/格子换算 | 网格值对象或网格服务 | UI、具体机器 |
| 地表类型和标签 | 地图状态 + TerrainRegistry | TileMap 贴图名 |
| 占用查询与登记 | GridOccupancy | 建筑 Sprite、放置预览 |
| 占地旋转计算 | Footprint 纯函数 | 各机器脚本 |
| 放置是否合法 | PlacementValidator | 鼠标控制器、UI |
| 放置/拆除事务 | PlacementService | View、输入处理 |
| 物品数量变化 | InventoryComponent API | 配方或传送带直接改数组 |
| 配方推进 | RecipeProcessingSystem | 机器场景 `_process()` |
| 科技图与解锁 | TechnologySystem / UnlockService | 科技树 UI |
| 固定时间推进 | SimulationRunner | 每台机器各自计时 |
| 地表逻辑状态 | TerrainState | TileMap 图块或贴图名 |
| 地表显示 | TerrainView / TileMapLayer | 模拟组件 |
| 传送带物品位置与拥堵 | 物流模拟系统 | 物品 Sprite |
| 动画、插值和特效 | EntityView / 表现层 | 模拟系统 |
| 场景节点创建 | EntityViewSynchronizer | 模拟系统 |
| 玩家提示与动画 | 表现/UI 层 | 领域组件 |
| 保存和迁移 | SaveService | 每个 View 自行写文件 |

## 11. 复用要求

- 预览调用正式验证器，不写“简化版”规则。
- 建造、蓝图、教程脚本和 AI 都调用同一个放置服务。
- 所有库存拥有者复用同一库存组件和转移 API。
- 所有方向旋转复用统一的格子方向与 Footprint 工具。
- 配方过滤通过标签/能力查询，不为每种机器写配方判断。
- 科技、地图生成和关卡限制通过组合规则或效果数据实现。
- 同一概念若在第三处出现，应提取为清晰的共享模块；不要提前建立无使用者的“万能框架”。

## 12. 提交前检查

- 新规则是否位于正确层，并有唯一权威来源？
- 是否可以通过组合现有组件完成？
- 模拟是否能在无场景、无渲染情况下运行？
- 输入预览与正式提交是否调用同一验证逻辑？
- 新内容是否有稳定 ID，所有引用是否能在启动时校验？
- 是否为核心成功、失败和边界情况添加测试？
- 是否影响存档格式；若影响，是否增加版本和迁移？
- 是否引入了隐藏的节点路径、Autoload 或全局信号依赖？
- 删除或隐藏 View 后，模拟结果是否保持不变？
- 表现优化是否在不改模拟规则的情况下可替换？
