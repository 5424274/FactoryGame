# 技术架构

## 1. 架构目标

项目需要长期承载大量机械方块、地表、配方、科技与解锁项。架构首先服务于以下目标：

- 新内容主要通过数据和组件组合加入，而不是不断复制脚本或扩展继承树。
- 模拟逻辑独立于场景树、渲染、输入和 UI，可在无界面环境中测试。
- 放置、拆除、旋转与占用检查只有一个权威实现。
- 配方、科技、建筑和地表之间使用稳定 ID 关联，避免资源路径和节点路径成为存档格式。
- 固定步长模拟具有确定性；显示帧率不改变生产结果。
- 系统之间依赖明确，可替换、可测试，并支持存档版本迁移。

核心设计思想是“组合优先于继承”。机械不是一棵不断变深的类继承树，而是“定义 + 若干能力组件 + 运行时状态”的组合。

## 2. 总体分层

依赖只能由外层指向内层：

```text
UI / 输入
    ↓ 命令与查询
应用层（建造、拆除、解锁、存取档用例）
    ↓
模拟层（世界状态、实体、组件、系统、事件）
    ↓
内容定义层（建筑、地表、物品、配方、科技 Resource）

表现层（场景、动画、音效）只读取模拟快照和事件，不拥有规则真相。
基础设施层负责资源加载、注册表、序列化和 Godot 适配。
```

### 2.1 内容定义层

使用自定义 `Resource` 保存设计数据。资源在游戏运行期间视为只读模板，不保存某局游戏的可变状态。

建议的顶层定义：

- `ItemDefinition`：物品 ID、名称、本地化键、图标、堆叠上限和标签。
- `TerrainDefinition`：地表 ID、标签、移动或建造属性和表现引用。
- `RecipeDefinition`：输入、输出、耗时、分类、机器能力要求和科技要求。
- `MachineDefinition`：机械 ID、占地、表现引用及能力组件列表。
- `TechnologyDefinition`：科技 ID、前置条件、研究成本及解锁效果列表。

所有定义都必须有稳定、唯一且不随文件移动而改变的 `StringName id`。跨定义引用保存 ID，不直接保存运行时对象引用。

### 2.2 模拟层

模拟层不读取鼠标、摄像机或控件，不创建 Sprite，也不依赖当前打开的场景。它包含：

- `WorldState`：当前地图、实体集合、库存、科技状态、模拟时钟和随机种子。
- `EntityState`：实体 ID、定义 ID、格子位置、朝向及运行时组件。
- 组件：一份实体拥有的数据或能力状态。
- 系统：批量处理某类组件的规则。
- 领域事件：已经发生的事实，例如建筑已放置、配方完成、科技已解锁。

逻辑时间使用固定步长。渲染节点可插值显示，但不得以 `_process(delta)` 直接推进生产状态。

### 2.3 应用层

应用层把玩家意图翻译成模拟操作，负责完整用例和事务边界，例如：

- `PlaceMachineCommand`
- `RemoveMachineCommand`
- `RotateMachineCommand`
- `SelectRecipeCommand`
- `StartResearchCommand`

命令先验证，再一次性提交。失败返回结构化结果，不允许只完成一半。

### 2.4 表现与 UI 层

- 世界表现节点根据实体 ID 创建或回收对应 View。
- UI 通过只读查询模型获取数据，通过命令请求改变世界。
- View 可缓存对显示资源的引用，但不能成为库存、占用或生产进度的权威来源。
- 动画结束不得决定模拟结果；模拟事件只触发表现反馈。

## 3. 模拟与画面渲染分离

本项目必须采用“逻辑实体与视觉实体分离”。这里的分离不是把渲染做成另一个程序，而是建立单向依赖：

```text
输入 / UI
    ↓ 命令
应用层
    ↓
模拟层 ← 内容定义
    ↓ 只读状态、快照、领域事件
表现层
    ├─ 地表渲染
    ├─ 机械和建筑显示
    ├─ 传送带及物品动画
    ├─ 特效与音效
    └─ 状态提示
```

表现层可以依赖模拟状态，模拟层不得依赖表现节点。删除全部 Sprite、动画、音效和 UI 后，模拟仍应能够正确运行、测试、保存和载入。

### 3.1 模拟层拥有的游戏事实

以下数据决定游戏结果，必须由模拟层权威保存：

- 每格的地表类型、资源和其他逻辑属性。
- 实体 ID、定义 ID、位置、朝向与占用格。
- 机械当前配方、库存、生产进度和工作状态。
- 物流网络连接关系及传送带上物品的逻辑位置。
- 电网供需、科技状态、解锁结果和任务进度。
- 模拟 tick、随机数状态及所有会影响确定性结果的数据。

这些内容不能只存在于 `Node`、`Sprite2D`、`TileMapLayer`、`AnimationPlayer` 或 UI 控件中。节点是否可见、是否在树中或是否播放动画，都不能改变模拟结果。

### 3.2 表现层拥有的显示状态

以下内容只影响玩家如何看到或听到结果，属于表现层：

- 纹理、模型、材质、层级和绘制方式。
- 动画播放、视觉插值、转轮速度和传送带移动效果。
- 粒子、音效、阴影、选择框和状态图标。
- 建筑放置预览的颜色、透明度和提示文字。
- 屏幕震动、镜头效果和非权威的临时缓存。

例如模拟层记录机器状态为 `WORKING`、进度为 `620 / 1000`；表现层可以据此播放工作动画并显示约 62% 的进度。产品何时生成由模拟 tick 决定，不能由动画完成信号决定。

### 3.3 逻辑实体与视觉实体

推荐的对应关系：

```text
WorldState
└─ EntityState[entity_id]
   ├─ 定义 ID
   ├─ 位置与朝向
   ├─ 库存组件
   ├─ 生产组件
   └─ 端口和其他组件

WorldView
└─ EntityView[entity_id]
   ├─ Sprite / 动画
   ├─ 状态图标
   └─ 特效与音效
```

`EntityViewSynchronizer` 以实体 ID 建立两者映射：

- 收到实体创建事件时实例化对应 View。
- 收到实体拆除事件时回收或删除 View。
- 每个显示帧读取必要的只读快照，更新动画和插值。
- View 丢失或重建不影响模拟；必要时可完全从 `WorldState` 重建画面。
- View 不可反向直接修改库存、占用、配方进度或科技状态，只能通过应用层提交命令。

模拟使用固定 tick 更新；表现可按显示帧率更新并在相邻模拟状态间插值。不得为了视觉平滑而改变权威模拟数据。

### 3.4 地表渲染

地表的权威状态和 TileMap 显示必须分离：

```text
TerrainState[cell] = terrain_id   # 权威模拟数据
TileMapLayer                      # 可替换的显示结果
```

地图生成、建造限制、资源分布和存档读取使用 `TerrainState`。`TileMapLayer` 根据状态生成或更新，不通过贴图名称反推出地表规则。这样可以替换 TileMap、分块绘制或其他渲染方式，而不改变地图逻辑。

### 3.5 传送带与大量物品渲染

传送带上的物品必须具有独立于 Sprite 的逻辑表示，包括所属线路、顺序或槽位、逻辑进度和物品 ID。表现层将逻辑进度转换为世界坐标并进行平滑显示。

原型阶段可以让一个逻辑物品对应一个 Sprite；规模扩大后可替换为对象池、批量绘制、`MultiMesh` 或自定义画布绘制。无论采用何种渲染优化，传送速度、拥堵、合流和产量结果都不得改变。

### 3.6 分离的收益与边界

这项分离保证：

- 帧率、可见性和动画速度不影响产量。
- 可以无窗口运行大规模模拟和自动化测试。
- 存档只保存游戏状态，不保存场景树。
- 更换美术、TileMap 或批量渲染方案时无需重写生产逻辑。
- 相机裁剪或暂时销毁远处 View 不会停止远处工厂。

相机、鼠标输入、UI、动画、音效和放置预览继续使用 Godot 节点。需要脱离表现节点的是所有决定游戏结果的状态与规则，而不是排斥 Godot 的场景系统。

## 4. 组合式机械模型

机械由三部分组成：

```text
MachineDefinition（静态模板）
├─ FootprintSpec
├─ PlacementRulesSpec
├─ InventorySpec × N
├─ RecipeProcessorSpec（可选）
├─ ItemPortSpec × N（可选）
├─ PowerConsumerSpec / PowerProducerSpec（可选）
├─ StorageSpec（可选）
└─ 其他独立能力组件

EntityState（本局实例）
├─ TransformComponent
├─ InventoryComponent × N
├─ ProcessorComponent（按定义生成）
├─ PortComponent × N
└─ 其他运行时状态
```

`Spec` 描述静态配置，运行时 `Component` 保存可变状态。两者不可混用。新增机械时应优先组合现有能力；只有出现独立规则和独立状态时才增加新组件。

### 4.1 推荐的基础能力

- `FootprintSpec`：相对格集合、旋转规则和占用层。
- `PlacementRulesSpec`：允许/禁止的地表标签、是否需要资源点、坡度等限制。
- `InventorySpec`：槽位、容量和物品过滤规则。
- `RecipeProcessorSpec`：支持的配方类别、并行数、速度倍率。
- `ItemPortSpec`：相对位置、朝向、输入/输出方向和过滤规则。
- `TransportSpec`：传送方向、容量、速度和连接规则。
- `PowerConsumerSpec` / `PowerProducerSpec`：功率及工作状态规则。
- `StorageSpec`：仓储行为；底层容量仍复用库存组件。
- `ResourceExtractorSpec`：资源类型、采集速度和地表/矿层要求。

不要创建 `FastAssembler extends Assembler extends Machine` 一类内容继承树。装配机型号之间的区别应尽量由组件参数和定义数据表达。

### 4.2 组件规则

- 组件只拥有自身状态，不直接查找场景节点。
- 组件之间不持有彼此的强引用；通过实体 ID、系统查询或明确端口通信。
- 跨多个组件的规则属于系统，不属于某个组件的 `_process()`。
- 组件类型要小而专一，不能出现包揽所有机械行为的 `MachineComponent`。
- 不为只有一个布尔值且没有独立规则的概念强行创建组件，可先作为相关 Spec 的字段。

## 5. 世界、地表与占用

### 5.1 坐标与地图

- 模拟统一使用 `Vector2i` 格子坐标。
- 像素/世界坐标换算仅由网格适配器提供。
- 地表按格存储 `terrain_id`，地表定义通过注册表查询。
- 可渲染 TileMap，但 TileMap 不是模拟数据的唯一来源。

### 5.2 占用是独立权威服务

`GridOccupancy` 是地块占用的唯一权威来源。任何系统不得维护第二份互不一致的占用字典。

占用键至少包含：

```text
(occupancy_layer, cell) -> entity_id
```

占用层用于区分地面建筑、地下物流、空中设施、资源点等可重叠类别。一个机械的实际占用格由 `FootprintSpec + origin + rotation` 纯函数计算。

服务应提供：

- 查询单格或格集合是否空闲。
- 查询某格上的实体。
- 原子预留与释放一组格子。
- 按实体 ID 反查全部占用格。
- 载入存档后的完整一致性校验。

### 5.3 统一放置判定流水线

所有预览、实际放置和 AI/脚本建造必须调用同一套 `PlacementValidator`，区别只是是否提交：

1. 定义和朝向是否合法。
2. 计算旋转后的全部占地格。
3. 检查地图边界。
4. 检查地表和资源点规则。
5. 检查占用层冲突。
6. 检查科技解锁、建造成本和其他前置条件。
7. 返回 `PlacementResult`，包含是否允许及全部失败原因。

成功提交时，扣除成本、创建实体和登记占用必须属于同一个事务。拆除按相反顺序执行，并先验证实体是否可拆、返还规则及输出物处理方式。旋转等价于“校验新占地并原子替换旧占地”，不能先释放旧格再尝试占用新格。

预览颜色和提示文本由 `PlacementResult` 驱动，禁止在 UI 中复制判定规则。

## 6. 配方系统

`RecipeDefinition` 建议包含：

- 稳定 ID 和本地化键。
- 一组 `ItemAmount` 输入和输出。
- 基础加工时长（以模拟 tick 或确定性时间单位表示）。
- 配方类别或能力标签，例如 `smelting`、`assembling`。
- 可选副产物、流体或催化剂扩展字段。
- 可选科技要求；最终可用性仍由解锁系统统一计算。

机器不保存硬编码配方列表。处理器声明自己支持的类别/标签，注册表建立“机器能力 → 可用配方”的索引。运行时处理系统负责：

1. 检查选中配方和解锁状态。
2. 检查并预留输入与输出空间。
3. 以固定步长累计进度。
4. 原子消费输入并生成输出。
5. 发布开始、暂停和完成事件。

库存操作必须通过统一 API 完成，配方系统不能直接修改字典或数组。

## 7. 科技与解锁

科技图和解锁结果分开建模：

- `TechnologyDefinition` 描述前置科技、成本和 `UnlockEffect` 列表。
- `TechnologyState` 只保存研究进度、已完成科技 ID 及必要版本信息。
- `UnlockService` 根据完成科技构建可用内容集合。

解锁效果采用组合数据，例如：

- 解锁机械定义 ID。
- 解锁配方定义 ID。
- 解锁建造类别或 UI 功能。
- 修改全局规则参数（仅在确有需要时使用明确类型的效果）。

科技树在载入内容时验证：ID 唯一、前置项存在、无非法环、所有效果目标存在。UI 只负责展示图，不自行推导解锁规则。

## 8. 注册表与内容校验

内容加载后进入只读注册表：`ItemRegistry`、`TerrainRegistry`、`RecipeRegistry`、`MachineRegistry` 和 `TechnologyRegistry`。

注册表通过 ID 查询定义，并在启动或测试阶段集中校验：

- ID 唯一且符合命名规范。
- 所有跨资源引用存在。
- 配方数量为正，耗时有效。
- 占地格不重复且包含合理原点。
- 机械端口没有非法重叠或方向。
- 科技图有效。
- 表现资源缺失时给出明确诊断。

内容错误应尽早失败，不能等玩家放置某台机器时才暴露。

## 9. 系统执行与事件

推荐的单次模拟 tick 顺序由 `SimulationRunner` 明确维护，例如：

1. 应用已排队命令。
2. 更新网络和物流连接。
3. 搬运物品。
4. 更新生产处理器。
5. 更新电力等辅助网络。
6. 汇总领域事件并生成只读快照。

具体顺序可随设计调整，但必须集中定义、写入测试，不能依赖节点在场景树中的偶然顺序。

事件分为两类：领域事件是模拟事实，可用于表现、统计或任务系统；UI 信号是界面交互通知，不进入模拟规则。不要把 Godot 全局信号总线当作隐藏依赖容器。关键模拟调用使用显式服务引用；信号适合一对多通知，不适合需要返回值的查询和事务。

## 10. 场景装配与依赖

主场景是组合根，负责创建并连接：内容注册表、世界状态与模拟运行器、应用服务和命令入口、世界表现同步器、输入控制器和 UI。

业务对象不得通过 `get_tree().root.get_node(...)` 寻找依赖。Godot 节点可通过导出 `NodePath`、初始化方法或构造工厂获得明确依赖。Autoload 仅用于真正跨场景且生命周期唯一的基础设施；不要把所有系统都做成单例。

## 11. 存档边界

存档只保存恢复模拟所需的数据：

- 存档格式版本和内容版本。
- 地图种子及发生变化的地表数据。
- 实体 ID、定义 ID、位置、朝向和运行时组件状态。
- 库存、配方进度、科技进度、模拟 tick 和随机数状态。

不保存 NodePath、节点实例 ID、纹理、PackedScene 或可重新计算的缓存。载入流程是：解析 DTO → 迁移版本 → 验证引用 → 创建状态 → 重建索引与占用 → 一致性检查 → 创建表现。

每类可持久组件负责自己的小型 DTO 转换，但总存档版本和迁移顺序由统一的 `SaveService` 管理。

## 12. 建议目录

```text
data/
  items/ terrains/ recipes/ machines/ technologies/
scripts/
  definitions/       # Resource 定义及静态 Spec
  simulation/
    core/             # WorldState、EntityState、tick、事件
    components/       # 运行时组件
    systems/          # 生产、物流、电力等系统
    grid/             # 地图、占用、Footprint 计算
  application/
    commands/         # 玩家意图 DTO
    services/         # 放置、拆除、研究等用例
  infrastructure/
    registry/         # 内容加载与校验
    persistence/      # 存档 DTO、迁移与序列化
  presentation/
    world/            # Entity View 同步、特效
    ui/               # 查询模型和 UI 控制器
  input/              # 输入到命令的转换
scenes/
  main/ world/ machines/ logistics/ ui/
tests/
  unit/ integration/ content/
```

场景目录按表现职责组织；模拟代码不要为了对应场景而放进场景目录。

## 13. 测试边界

- 纯函数单元测试：坐标、旋转占地、配方计算和科技图。
- 系统测试：库存、生产、物流和固定 tick 的确定性。
- 应用服务测试：放置、旋转、拆除事务及失败原因。
- 内容测试：注册表完整性和所有数据引用。
- 集成测试：存档往返、完整生产链和表现同步。

至少要长期保留以下不变量测试：同一格同一占用层不能属于两个实体；实体占用反向索引一致；库存数量不为负；锁定内容不能建造或选择；相同初始状态和命令序列产生相同结果。

## 14. 当前原型迁移方向

现有 `WorldGrid` 可逐步拆成“纯网格坐标/地图数据”和“网格绘制/悬停表现”。现有 `BuildingPlacement` 同时承担输入、预览、验证、占用和创建显示节点，后续应拆为：

- `BuildInputController`：收集鼠标与快捷键并发出命令。
- `PlacementPreview`：显示 `PlacementResult`。
- `PlacementService`：完成统一验证和事务提交。
- `GridOccupancy`：保存权威占用状态。
- `EntityViewSynchronizer`：根据实体事件创建或移除表现节点。

迁移应按功能增量进行，不需要为了架构一次性重写原型。

## 15. 已确定的基础设计决策

本节固定实体标识、组件存储和依赖方向三项基础选择。它们适用于当前原型向独立模拟架构迁移的阶段；只有真实功能或性能数据证明不足时才升级，不提前建立通用 ECS 或依赖注入框架。

### 15.1 实体 ID

定义 ID 与实体 ID 是两种不同概念：

- 定义 ID 使用稳定的 `StringName`，例如 `base:assembler_1`，表示实体属于哪种内容定义。
- 实体 ID 使用 64 位 `int`，表示本局游戏中的某一个具体实例。

`WorldState` 是实体 ID 的唯一分配者，使用从 `1` 开始的单调递增序列；`0` 表示无效 ID。实体删除后 ID 不复用，存档保存 `next_entity_id`，载入时验证所有实体 ID 唯一且大于零。

不得使用节点实例 ID、`NodePath`、资源路径或格子坐标充当实体 ID。表现层可维护 `Dictionary[int, Node2D]` 形式的 View 映射，但该映射只是可重建缓存，不能决定实体是否存在。

当前单机需求不使用 UUID。未来若出现联机或跨存档导入，通过导入阶段的 ID 重映射解决，不提前增加运行时复杂度。

### 15.2 组件存储

初期采用类型化 `EntityState` 与可选能力状态的组合，不采用字符串到 `Variant` 的通用组件字典，也不建立完整 ECS。

```text
EntityState
├─ id: int
├─ definition_id: StringName
├─ cell: Vector2i
├─ rotation: int
├─ inventories: Array[InventoryState]
├─ processor: ProcessorState 或 null
└─ transport: TransportState 或 null
```

共同身份和空间状态直接属于 `EntityState`。同类能力可能存在多个实例时使用类型化数组，例如一台机器可以有输入、输出和燃料库存，每个库存使用实体内稳定的局部 ID。当前只需要一个实例的能力可先使用可空的类型化成员；出现真实的多实例需求后再改为集合。

系统初期可以遍历实体并按能力筛选。若性能分析证明全表扫描成为瓶颈，再增加按组件类型维护的实体 ID 索引。索引必须能从权威实体状态重建，不作为存档真相。

只有在大量实体扫描成为实际瓶颈、能力需要频繁动态增删、组件组合显著增加，或类型化实体产生大量无关字段时，才评估迁移到完整 ECS。升级内存布局时应尽量保持实体 ID 和存档 DTO 契约稳定。

### 15.3 依赖方向

项目使用显式依赖注入，主场景作为组合根，不引入服务容器或依赖注入框架。

```text
表现 / UI / 输入
        ↓
      应用层
        ↓
      模拟层 ← 只读领域定义
        ↑
基础设施负责加载、转换、校验和持久化
```

各层约束如下：

- 模拟层可以使用 `Vector2i`、`StringName` 等稳定值类型以及纯 GDScript 状态对象，但不依赖 `Node`、场景树、输入、UI、纹理、音频、`PackedScene` 或资源路径加载。
- 内容定义由基础设施加载和集中校验，再通过只读注册表提供。模拟层不得调用 `load()`、修改共享 `Resource` 或把 Resource 对象写入存档。
- 原型阶段可以直接把经过校验的只读 Resource 作为定义对象使用；当无 Godot 资源环境测试、版本迁移或定义复杂度产生真实需求时，再转换成独立领域定义，避免过早维护两套重复模型。
- 应用层协调完整用例和事务，可依赖世界状态、占用、定义查询、验证器及领域服务，但不读取鼠标、不创建 Sprite，也不生成玩家文案。
- 基础设施可以依赖模拟层的数据契约，负责资源加载、注册表、DTO 序列化、文件读写和迁移；模拟层不能反向调用基础设施。
- 表现层通过实体 ID、只读查询和领域事件同步 View。表现缓存可以随时由世界状态重建。

依赖由组合根通过初始化方法或明确工厂传入。业务对象不得在内部搜索根节点、读取全局单例，或同时提供显式依赖和隐式回退路径。Godot 节点的导出引用或 `NodePath` 只用于场景装配，不进入模拟状态和存档。

### 15.4 最小权威模型

第一阶段采用以下最小结构：

```text
WorldState
├─ next_entity_id: int
├─ entities: Dictionary[int, EntityState]
├─ occupancy: GridOccupancy
├─ simulation_tick: int
└─ random_state

DefinitionRegistry
└─ definitions_by_id（只读并在启动时校验）

表现层
└─ views_by_entity_id: Dictionary[int, Node2D]（可重建缓存）
```

`WorldState` 是本局状态的权威来源，`GridOccupancy` 与其共享生命周期。注册表保存静态定义，View 映射只负责表现。存档保存实体和组件 DTO，不保存 View、节点引用或 Resource 对象。

### 15.5 第一阶段迁移范围

第一阶段只围绕现有 1×1 测试建筑贯通一条垂直链路：

```text
鼠标位置
→ PlaceMachineCommand
→ PlacementValidator
→ PlacementService
→ EntityState + GridOccupancy
→ MachinePlacedEvent
→ EntityViewSynchronizer 创建 Sprite View
```

本阶段只实现最小 `MachineDefinition`、`EntityState`、实体 ID 分配、`FootprintSpec`、`GridOccupancy`、`PlacementResult`、`PlacementValidator`、`PlacementService` 和表现同步。链路通过测试后再加入多格占地、旋转和拆除；库存、配方、科技、完整注册表体系及通用 ECS 不作为这一阶段的前置条件。
